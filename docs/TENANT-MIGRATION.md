# Upgrade beta.2 to tenant connections

This is a coordinated cutover. Old clients need `/mcp/<tenant>` URLs, browsers
must install the matching extension and re-pair, and old grants remain invalid.
There is no unscoped compatibility endpoint.

## Detect and preview

Before restarting the upgraded service, find the configured `DOMAGENT_DB` path
and use the read-only preview:

```sh
node domagent-mcp/migrate.js preview /path/to/domagent.db
```

Preview lists legacy client IDs/owners and linked browser owners, not credentials.
For every legacy client, explicitly choose a separate tenant owner, label, and
admitted browser members. Do not infer ownership from the calling application's
internal identifiers.

Assignments file example (local operator artifact, not source code):

```json
[
  {
    "client_id": "<existing-client-id>",
    "owner_id": "<existing-owner-id>",
    "label": "Atlas",
    "members": ["<other-authorized-owner-id>"]
  }
]
```

Tenant IDs are generated by the migration. Every existing client, including
revoked clients, must be assigned exactly once; no two clients share a tenant.
Credential hashes and revocation states are preserved. Membership requires an
existing account; owners/member invitations remain independently administered.

## Stop, back up, migrate

Stop the actual service unit before making a consistent SQLite backup. For the
user-level installation this is `systemctl --user stop domagent.service`.
After confirming it stopped, copy its closed database to a restricted backup.
Do not copy a live WAL database as if it were a consistent backup.

```sh
node domagent-mcp/migrate.js apply /path/to/domagent.db /path/to/assignments.json --service-stopped
```

The command requires an explicit stopped-service acknowledgement. It validates
complete assignments, applies the schema transactionally, reports generated
tenant IDs, and refuses repeat migration. The flag does not stop your service
for you. The operator is responsible for stopping any other writers.

Legacy owner identities persist. Owner sessions are cleared. Legacy clients and
devices remain archived in private tables; legacy device keys cannot authenticate
the new service. Pending enrollment and old links are retired.

## Configure and verify

Update each client application to `https://your-server/mcp/<assigned-tenant>`,
using its own scoped credential-management mechanism. Validate intended endpoint
injection; do not paste real credentials into chat or source/config files exposed
to the agent.

Start the service, verify `/health` and `/.well-known/domagent`, sign in to
`/dashboard`, then install the matching extension ZIP and paste the assigned
public `https://your-server/join/<tenant>` link. Approve connection; no sharing
should activate until the user explicitly approves a new local request.

Test old `/mcp` and v1 proofs are rejected, another tenant's token fails, existing
revoked tokens stay revoked, and each owner sees only permitted connections.

## Rollback

Stop the service. Restore the consistent beta.2 backup and matching beta.2 code
and extension versions, then restore/revalidate the prior client endpoint
configuration. Never run old code against migrated tables or restore only one
part of a live SQLite/WAL database. Rotate credentials if the backup resurrects
credentials revoked after it was taken.
